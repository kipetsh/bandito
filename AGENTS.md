# AGENTS.md

## Сводка по проекту

Bandito — карточная игра (адаптация настольной игры Bandido от Helvetiq) на HTML5, Vanilla JS и CSS. Для разработки и публикации используется Vite; приложение остаётся vanilla JS и работает на GitHub Pages. Поддерживает одиночный режим (2, 5, 6 выходов) и кооперативный онлайн-мультиплеер до 4 игроков через Firebase Realtime Database.

## Обязательное правило: ESLint и Prettier

Перед написанием или изменением кода **обязательно изучить и соблюдать действующие конфиги проекта**: `eslint.config.mjs`, `.prettierrc.json` и `.prettierignore`. Не полагаться на личный стиль, память или настройки редактора. Код сразу писать в соответствии с этими правилами; перед проверкой форматировать все затронутые файлы через Prettier с учётом правил проекта. Не отключать, не ослаблять и не обходить правила ESLint/Prettier ради прохождения проверки без отдельной обоснованной необходимости. Исключения из `.prettierignore` соблюдать: не форматировать игнорируемые файлы целиком, если задача не требует их изменения; при точечном изменении форматировать только нужный участок безопасным способом.

**Перед отправкой любого изменения обязательно запускать `npm run check`.** Если проверка сообщает ошибки, исправить весь список диагностик и повторять проверку до полного успеха. Для ChatGPT без локального клона запуск выполняется GitHub Actions в проверочной ветке; нужно разбирать полный лог шага, а не только последние строки.

## Ключевые соглашения и правила работы

### 1. Правило коммитов

- **Коммитить только явно выбранные файлы:** добавлять в индекс только целевые пути. Запрещены слепые команды `git add .`, `git add -A` и `git commit -a`.
- **Обычный режим разработки:** после каждой логически завершённой группы изменений форматировать затронутые файлы и запускать `npm run check`; для полной проверки проекта — `npm run check && npm run test`. Не коммитить изменения, пока обязательные проверки не завершились успешно.
- **Специальный режим ChatGPT + GitHub Plugin:** если у ChatGPT нет прямого доступа к терминалу клона, применять отдельный процесс из раздела 6. Этот вариант предназначен только для чата ChatGPT с GitHub Plugin, а не для любого агента.
- **Никаких заявлений о проверке без фактического запуска:** указывать, где именно прошли проверки — в терминале клона, в GitHub Actions на точном SHA проверочной ветки или в GitHub Actions.

### 2. Синхронизация документации

- При любых изменениях архитектуры, механик, правил интерфейса или состава файлов **всегда обновлять `README.md` и `AGENTS.md`**, сохраняя их в актуальном состоянии.
- `AGENTS.md` хранит решения, правила и подводные камни, а не пересказ кода: имена функций, классов и конкретные значения пишем, только если без них правило непонятно. Подробности реализации — в комментариях к коду.

### 3. Графика и адаптивность

- **Сохранение оригиналов:** исходные качественные изображения всегда хранятся в проекте (`assets/images/`) и никогда не перезаписываются оптимизированными версиями.
- **Оптимизированные копии в интерфейсе:** в игру попадают только оптимизированные копии — их делает сборка (WebP, ограничение размера), руками не готовим.
- **Retina и экраны:** игра должна быть оптимизирована под экраны Retina (High-DPI / @2x), графика и элементы поля не должны размываться. Размеры, от которых зависит положение мелких элементов (точки на поле), держим целыми и чётными, чтобы они не съезжали на полпикселя.
- **Мобильные и десктопные экраны:** интерфейс, камера поля, перетаскивание и управление картами должны одинаково гладко и удобно работать как на смартфонах/планшетах, так и на десктопе. Граница телефона — 760px: на узком экране рука лежит в нижней шторке, базовая клетка поля меньше.

### 4. Игровые правила и интерфейс партии

#### Единое поведение

- Мышь, касание и клавиатура приводят к одним и тем же состояниям разными событиями; никаких особых веток под отдельный флоу, тему или устройство, кроме перечисленных ниже осознанных различий.
- Одиночная игра и онлайн ведут себя и выглядят одинаково (старт, выбор, ход, рука, поле).

#### Рука

- У карты в руке два независимых состояния. **Указанная** — под наводящимся указателем или под фокусом с клавиатуры; такая карта одна (последняя, на которую указали), она не поднимается, а только светлее и с рамкой потолще, партию не меняет и точек не показывает. **Выбранная** — после клика, тапа, Enter, пробела или клавиш 1/2/3; она приподнята, с той же рамкой и полоской снизу, на поле показаны её точки и (кроме выбора мышью, см. ниже) превью.
- Приподнята только выбранная карта. Подъём и полоска анимируются переходами, поэтому рука перерисовывается на месте (кнопки оставшихся карт не пересоздаются) — иначе ломаются переходы, `:hover` (карта под курсором моргает) и фокус.
- Рамка карты на поле и в руке — `outline`, центрированный на краю: утолщение не меняет размер карты, а рамки соседних карт на поле сливаются в одну линию. `border` для рамок не использовать — он сдвигает сетку клеток. Осветление стен — цветом, не `filter` (он стирает линии клеток).
- Карты в руке — одна радиогруппа с roving tabindex: Tab попадает в неё один раз, стрелки переносят фокус по кругу. Кольца фокуса у карт нет — его роль играют подсветка и рамка.
- Каждая миниатюра случайно повёрнута на 0° или 180° один раз на карту и не переворачивается при перерисовке или выборе точек.
- Взятая из колоды карта встаёт на место сыгранной, остальные не сдвигаются; новая карта один раз подлетает снизу, сыгранная просто исчезает. Если колода пуста, оставшиеся карты сдвигаются влево без анимации. Фокус в руку ставится без прокрутки страницы.

#### Выбор положения на поле

- При выборе карты показываются допустимые положения сразу для всех четырёх поворотов, у каждого поворота свой цвет точки; одинаковые повороты симметричной карты показываются одной точкой. Отдельной кнопки поворота нет и не будет.
- Превью — одно показанное положение выбранной карты (пунктирная карта, увеличенная точка, кнопки «Отмена» / «Поставить»). Новое превью встаёт под курсор, если он над одним из положений. Иначе после клавиатуры или тапа оно встаёт в первую позицию круга, а после мыши не показывается: видны только точки, превью появится при наведении на поле (курсор всё равно идёт туда). Чем было последнее нажатие — мышью, касанием или клавишей, — игра запоминает по `pointerdown` / `keydown`.
- Целью наведения и нажатия служит вся область, которую закрыла бы новая карта, а не только точка; при перекрытии выигрывает положение с ближайшей точкой. Точки — декоративные и фокус не получают.
- Наведение двигает только превью, без перерисовки поля. Наведением считается лишь реальный сдвиг указателя без нажатых кнопок: Chrome повторяет `pointermove` после перерисовки, и неподвижный курсор не должен отбирать превью у стрелок.
- Клик мышью по показанному положению ставит карту, по другому — показывает его. Тап только показывает: на касании карта ставится лишь кнопкой «Поставить», чтобы случайный второй тап не сделал ход. Клик после перетаскивания камеры ничего не делает; нажатие на поле не забирает фокус.
- Стрелки вне руки обходят все положения по одному кругу по часовой стрелке вокруг центра выложенных карт (повороты одного места идут подряд); камера следует за превью.
- Точка стоит в центре будущей карты. Все карты 6×3 и лежат на сетке с шагом 3 клетки, поэтому в одном центре сходятся максимум два поворота; их точки разнесены по длинной оси на ±0,62 клетки — при таком сдвиге расстояния до всех соседних точек равны (~1,24 клетки) и точки не накладываются. Размер точки растёт с зумом медленнее клеток, чётными шагами.

#### Ход, отмена и фокус

- Esc и «Отмена» снимают выбор и возвращают фокус на карту. Повторный клик или тап по выбранной карте тоже снимает выбор; Enter, пробел и 1/2/3 на выбранной карте выбор сохраняют, чтобы клавиатура всегда вела к установке. Уход фокуса с клавиатуры из руки и кнопок превью снимает выбор; клик мышью в другом месте, перерисовка и уход из окна — нет.
- После хода выбранным остаётся тот же слот (или левый, если слота нет), и его превью сразу показывается (по тем же правилам: после мыши — только под курсором). Исключение — ход с клавиатуры: выбор снимается, фокус встаёт на карту в слоте, чтобы стрелками выбрать следующую.
- Если перерисовка спрятала элемент с фокусом, фокус возвращается в руку. В онлайне на чужом ходу карты заблокированы; когда очередь вернулась, фокус возвращается в руку, а статус «Твой ход» не затирает подсказку выбора положения.
- **Старт партии:** камера по центру, ничего не выбрано, фокус на первой карте и она указана (подсвечена) — независимо от того, начали мышью или клавиатурой. На телефоне карту за пользователя не выделяем: фокуса и подсветки нет.

#### Поле и камера

- Игровая область — выложенные карты плюс 9 клеток (полторы карты) с каждой стороны; поле — объединение области и текущего вида камеры, поэтому прокрутка есть только для части, выходящей за вид.
- Установка карты не двигает камеру: карты остаются в тех же точках экрана. Зум и изменение размера окна сохраняют клетку в центре вида. При переходе через 760px масштаб сохраняется в процентах.
- Масштаб: 100% — клетка 24px (на телефоне 18px), шаг 2px, примерно 50–150%; партия начинается со 100%. Значение масштаба — подпись, а не кнопка. Клавиши +/− меняют масштаб.
- Последняя поставленная карта (кроме стартовой) помечается жёлтой точкой, масштабируемой с зумом; её рамка не меняется. Углы карт на поле прямые, в руке скруглены.
- Анимация новой карты на поле проигрывается строго один раз в момент хода и не перезапускается при перерисовке: плавное увеличение и возврат на месте, без смещения и отскока.

#### Подсказки

- Строка статуса подсказывает текущий шаг. На десктопе подсказки упоминают клавиатуру («…, либо ←→ и Enter.»), на телефоне — нет, и после выбора карты подсказывают нажать «Поставить».

#### Правила игры

- **Колода и сброс:** сброшенные карты уходят под низ колоды, взятие — всегда сверху. Сброс разрешён только при отсутствии доступных ходов.
- **Одиночная игра из лобби:** кнопки одиночных режимов доступны рядом с лобби кооператива, поэтому старт одиночной партии сначала выходит из комнаты — иначе карты в руке остаются заблокированными.
- **Таймер хода:** истечение 60 секунд в онлайне только передаёт очередь, карты в руке сохраняются.

### 5. Архитектура стилей (дизайн-система)

#### Структура и слои

- Слои: `@layer tokens, base, components, blocks, utilities;` (объявлены в `css/tokens.css`). Каждый файл целиком лежит в своём слое, поэтому специфичность между слоями не важна.
- `css/tokens.css` — единственное место с «сырыми» значениями: цвета, шрифты, размеры, отступы, радиусы, тени, z-index. Тёмная тема — только переопределение переменных в `.dark-theme` в этом же файле.
- `css/base.css` — сброс и умолчания. Селекторы по тегам разрешены только здесь.
- `css/components/` — переиспользуемые компоненты, `css/blocks/` — блоки экранов, `css/utilities.css` — `.hidden`, `.visually-hidden`, уменьшение анимаций.
- Новый файл стилей подключается в `index.html` в порядке: tokens → base → components → blocks → utilities.

#### Правила, готовые к CSS-модулям

- Один блок — один файл, плоский BEM: `.block`, `.block__element`, `.block--modifier`. Файл стилизует только свои классы.
- Запрещены `!important`, селекторы по ID и селекторы с классами чужого блока. Композиция — несколько классов на одном элементе (`class="card card--glass menu__card"`).
- Два модуля на одном элементе не объявляют одно и то же свойство. Блок настраивает компонент через его публичные переменные (`--card-padding`, `--hand-card-cell` и т. п.); компонент читает их с фолбэком и сам не объявляет.
- Медиазапросы лежат в файле своего блока.
- Анимации (`@keyframes`) называются с префиксом блока: `board-tile-drop`, `end-screen-pop`.
- Для модальных окон не анимировать `backdrop-filter`/`filter`: радиус размытия держать статичным и умеренным, а проявление слоя выполнять через `opacity`; содержимое анимировать только через `opacity` и `transform`. Длительность открытия и закрытия держать короткой и согласованной с JS-таймером закрытия.

#### JS и классы

- JS находит элементы по `id` и `data-*`, а не по стилевым классам.
- Состояние — через модификаторы БЭМ и `.hidden`. Инлайновые цвета и `style.display` запрещены; инлайн допустим только для вычисляемой геометрии (позиции и размеры на поле) и случайных параметров конфетти.
- **Снекбар:** разовые сообщения о результате действия (скопирован код, вышел из комнаты, отказ, ошибки сети) — только через `snackbar(text, kind)`; они исчезают сами. Все ошибки действий и сети показываются только снекбаром. Точку в конце сообщения снекбара не ставим. Постоянные инструкции, подсказки и текущее состояние (строка статуса, таймер хода) остаются на странице.

#### Цвета

- Только переменные из `tokens.css`. Близкие, неразличимые на глаз оттенки сводятся в один токен.
- Используем семантические токены (`--color-text*`, `--color-surface*`, `--color-border*`, `--color-control*`, `--color-primary*`, `--color-accent*`, `--color-success*`, `--color-danger*` и т. п.), а не произвольные.

#### Отступы и размеры

- Все отступы, зазоры и размеры контролов кратны 4px (`--space-*`). Значения не из шкалы допустимы только для геометрии иллюстраций и анимаций.
- Иерархия: чем выше уровень или сильнее различие между элементами, тем больше отступ. Внутри элемента — 4–8, между элементами группы — 8–12, между группами внутри карточки и между карточками — 16–24, поля страницы — 16–56.
- Радиусы: 8 / 12 / 16 / 20 / 28 / `full`. Высоты контролов: 36 / 44 / 52.

#### Типографика

- Шкала: 12, 14, 15 (базовый текст), 16, 18, 20, 24, `--text-display` для финального экрана. Минимум — 12px, там, где хватает места, — 14px. Не мельчить шрифт ради вмещения — переносить строки или менять формулировку.
- Шрифты: `--font-sans` (системный) для текста, `--font-serif` (Merriweather 700) для заголовков, `--font-mono` для кода комнаты.
- `letter-spacing` используется только у кикера «Карточная игра · 1–4 игрока». Больше нигде.
- В HTML текст пишется в обычном регистре (с большой буквы), капс — только через CSS.
- Новый заголовок или подпись берут существующую текстовую роль (заголовок, подзаголовок, подпись, заголовок пункта, кикер), а не собственные стили.

### 6. Сборка, проверки и форматирование

- **Среда:** Node.js не ниже 22.12.0 (`.nvmrc`, `package.json`).
- **Установка:** только `npm ci`. `package-lock.json` хранится в репозитории; при изменении зависимостей коммитить и `package-lock.json`, и `package.json`.
- **Команды:** `npm run check` независимо запускает Prettier и ESLint и показывает результаты обоих инструментов, даже если один завершился с ошибкой. Оба инструмента должны выводить полный список найденных проблем, без намеренного ограничения количества диагностик. `npm run test` запускает исходные тесты, production-сборку и тесты результата сборки. `npm run build` отдельно создаёт production-сборку; `npm run test:build` проверяет уже собранную папку `build/`.
- **Автоисправления:** при редактировании сразу соблюдать правила ESLint и Prettier. Перед проверкой форматировать затронутые файлы. `npm run check:fix` выполняет автоисправление ESLint и форматирование проекта; для точечной работы допустимы `npx prettier --write <файлы>` и `npx eslint <файлы> --fix`. После автоисправлений обязательно повторно запускать `npm run check`.
- **Коммиты и проверки:** обычный агент с локальным клоном обязан форматировать затронутые файлы и запускать `npm run check` до отправки изменений в целевую ветку; для полной проверки также запускать `npm run test`. Если прямого локального терминала нет, ChatGPT + GitHub Plugin использует GitHub Actions как исполняемую среду: изменения отправляются только в парную проверочную ветку `BRANCH-chatgpt-check`, а в целевую ветку они переносятся только после успешных Actions-проверок. Не утверждать, что локальные команды запускались, если они фактически не запускались.
- **Специальный процесс ChatGPT + GitHub Plugin — только для ChatGPT:** этот вариант предназначен для чата ChatGPT с GitHub Plugin, когда нет прямого терминального доступа к клону репозитория. Он не является универсальной инструкцией для Claude, Codex, Antigravity, IDE или обычного локального терминала.
- **Единая инфраструктура:** общие инструменты и workflow находятся в основном репозитории, начиная с `main`: `package.json`, `package-lock.json`, `tools/check.mjs`, `.prettierignore`, `.github/workflows/check.yml` и этот раздел `AGENTS.md`. Проверочная ветка содержит только изменения приложения и документации по задаче, а не отдельную инфраструктуру для переноса.
- **Один CI workflow без дублирования:** единственный основной workflow — `.github/workflows/check.yml`. Отдельных `pages.yml` и `chatgpt-check-bundle.yml` нет. Не добавлять параллельные workflow, повторяющие `npm ci`, проверки, тесты, production build или deployment.
- **Когда запускается CI:**
    - Pull request с целевой веткой `main`: `npm ci`, `npm run check`, затем `npm run test`. Pages deployment не выполняется.
    - Push в `main`: те же проверки и тесты; после их успешного завершения workflow использует созданную тестами папку `build/`, загружает Pages Artifact и выполняет deployment. Не запускать отдельный второй `npm run build`: команда `npm run test` уже выполняет production build и тесты сборки.
    - Push в ветку с окончанием `-chatgpt-check`: запускаются те же `npm ci`, `npm run check` и `npm run test`. Никакие исходники, `node_modules` или снимки проекта в Artifacts не упаковываются.
    - `workflow_dispatch`: запускает проверки выбранной ветки. Ручной запуск не публикует Pages; публикация выполняется только после push в `main`.
- **Работа ChatGPT по логам GitHub Actions:**
    1. Получить HEAD целевой ветки и проверить парную `BRANCH-chatgpt-check`. Проверочная ветка должна начинаться от актуального HEAD целевой ветки и содержать только изменения для текущей задачи.
    2. Внести связанные изменения одним логическим набором, отформатировать затронутые файлы и создать один коммит с явным списком путей. Не использовать `git add .`, `git add -A` или `git commit -a`.
    3. Отправить коммит в `BRANCH-chatgpt-check` и дождаться завершения соответствующего запуска GitHub Actions. Workflow отдельно выполняет `npm run check`, а после его успеха — `npm run test`.
    4. Если `npm run check` завершился ошибкой, получить полный лог шага из Actions, разобрать все сообщения Prettier и ESLint, сгруппировать проблемы по файлам и исправить их за один логический проход. Не ограничиваться последними строками лога и не исправлять только первую найденную ошибку. Если лог длинный, извлекать его целиком и выводить/обрабатывать частями, сохраняя все диагностические сообщения. Если упал `npm run test`, аналогично использовать полный лог соответствующего шага. После исправлений снова отправить проверочную ветку и повторить цикл.
    5. Не переносить изменения в целевую ветку, пока `npm run check` и `npm run test` не завершились успешно на одном и том же HEAD проверочной ветки. Затем убедиться, что HEAD целевой ветки не изменился, перенести в неё ровно проверенный коммит и дождаться успешного Actions; для `main` также дождаться Pages deployment. Логи успешных запусков без причины не скачивать.
- **Параллельные ветки:** пары `feature-1` ↔ `feature-1-chatgpt-check` и `feature-2` ↔ `feature-2-chatgpt-check` используют один и тот же workflow. Проверки относятся только к конкретным ветке и SHA и не взаимозаменяются.
- **Выход сборки:** `build/` генерирует Vite, он игнорируется Git и не редактируется вручную. GitHub Pages публикует только `build/`, созданную успешным `npm run test` на push в `main`.
- **Модули:** единственная точка входа — `js/main.js`, модули связаны явными `import`/`export`, глобальных переменных нет (кроме `firebase` из CDN). Состояние партии — объект `state` из `js/game.js`; другие модули меняют его поля, а не переприсваивают импорт.
- **Импорты только через алиасы** `#js/*` и `#assets/*` (subpath imports в `package.json`); относительные пути запрещены и ловятся ESLint.
- **Ресурсы:** изображения подключаются импортами и собираются Vite; JSON колоды из `resources/` копируется в сборку как есть, потому что грузится через `fetch()`. При сборке изображения конвертируются в WebP (если WebP не больше исходника); исходники в `assets/images/` не меняются.
- **Preload:** `index.html` заранее грузит фоны и логотипы; не убирать эти подсказки без сопоставимой замены.
- **Pre-commit и CI:** перед коммитом `lint-staged` проверяет и форматирует staged-файлы. Основной CI выполняет проверки и тесты на pull request в `main`, на push в `main` и на push в `*-chatgpt-check`; Pages публикуется только после успешного CI на push в `main`.
- **Prettier:** 4 пробела (JSON и YAML — 2), ширина 120, одинарные кавычки, LF. Legacy UI-файлы исключены из глобальной проверки, чтобы не плодить whitespace-only diff; staged-файлы форматируются всегда.
- **Тесты** проверяют поведение (запускают код), а не текст исходников.
- **Временные файлы:** временные скрипты и скриншоты кладём в `.tmp/` в проекте (игнорируется Git, ESLint и Prettier), а не в системный `/tmp`; скриншоты проверок после проверки не удаляем.
- **Браузерные проверки:** проверять на уже запущенном `npm run dev` (`http://localhost:3000`); второй Vite не запускать — в конфиге `server.open: true`, и каждый запуск открывает вкладку в браузере пользователя (если сервер не запущен — спросить или запускать с `--open false`, для сборки — `vite preview --open false`). После проверок Playwright удалять `.playwright-mcp/`. В headless-браузере `:hover` ненадёжен — состояние проверять по классам и элементам, а не по вычисленным стилям наведения. Касание проверять в контексте с `hasTouch`, а не кликом мыши в узком окне.
- **Дизайн:** настройка сборки не повод менять HTML-структуру, стили, анимации или игровую логику. Визуальные изменения — только по отдельному запросу.
- **После правок:** форматировать затронутые файлы и запускать `npm run check`; для полной проверки проекта — `npm run check && npm run test`.
