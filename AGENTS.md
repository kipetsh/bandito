# AGENTS.md

Инструкции для агентов: соглашения, правила репозитория и подводные камни. Описание игры, интерфейса и инфраструктуры — в [README.md](README.md) и [docs/](docs/):

- [docs/game-ui.md](docs/game-ui.md) — интерфейс партии: рука, выбор положения, поле, камера, подсказки;
- [docs/challenges.md](docs/challenges.md) — пользовательские испытания и их редактор, правила Firebase;
- [docs/ci.md](docs/ci.md) — GitHub Actions и порядок проверок;
- [docs/build.md](docs/build.md) — сборка, ресурсы и оптимизация изображений;
- [docs/native-apps.md](docs/native-apps.md) — приложения Tauri 2 и OTA-обновления.

Bandito — карточная игра (адаптация Bandido от Helvetiq) на HTML5, Vanilla JS и CSS: веб-версия на Vite и GitHub Pages, приложения на Tauri 2 с общей веб-кодовой базой, одиночный режим и кооператив до 4 игроков через Firebase Realtime Database.

## 1. Git и коммиты

- **Единая рабочая ветка — `main`.** Не создавать feature-ветки. Исключение — проверочная ветка `*-chatgpt-check` в режиме без среды запуска (см. раздел 2) или ветка, которую явно запросил пользователь.
- **Не переписывать историю без прямой просьбы:** каждая новая правка — новый коммит. Не вливать изменения в предыдущие коммиты (`--amend`, `--fixup`, rebase, squash), если пользователь не попросил об этом специально; особенно в `main` и особенно в коммиты, уже отправленные в origin. Force push — только по явному запросу.
- **Коммитить только явно выбранные файлы:** добавлять в индекс только целевые пути. Запрещены `git add .`, `git add -A` и `git commit -a`.
- **Одна задача — один push:** сначала выполнить весь согласованный объём задачи, затем отправить все её коммиты одной операцией, чтобы CI проверил итоговое состояние, а не промежуточные.
- **Никаких заявлений о проверке без фактического запуска:** указывать, где именно прошли проверки — в терминале клона или в GitHub Actions на точном SHA.

## 2. Проверки

Перед написанием кода изучить и соблюдать `eslint.config.mjs`, `.prettierrc.json` и `.prettierignore`, а не личный стиль или настройки редактора. Не отключать и не ослаблять правила ради прохождения проверки. Файлы из `.prettierignore` целиком не форматировать, если задача их не меняет; staged-файлы форматирует pre-commit hook (`lint-staged`).

- **Есть среда для запуска npm (локальный клон):** перед каждым коммитом форматировать затронутые файлы и запускать `npm run check` и `npm run test`. Коммитить только код, который проходит проверки и тесты. Если они прошли локально, после push ждать GitHub Actions не нужно: задача завершена, результат CI не отслеживать.
- **Среды нет (чат ChatGPT с GitHub Plugin):** внести завершённый набор изменений в `main` и отправить; в конце задачи, после публикации Pages, дождаться Frontend checks на этом SHA (он запускается сам при push в `main`, вручную не запускать). Если он упал — взять логи из этого запуска, запушить исправления в ветку `*-chatgpt-check` (например, `main-chatgpt-check`), а когда проверки в ней прошли — перенести исправления в `main`, где Frontend checks снова запустится автоматически. Подробности — в [docs/ci.md](docs/ci.md).
- `npm run check` — Prettier и ESLint, оба выводят полный список проблем. `npm run test` — исходные тесты, production-сборка и тесты сборки. После автоисправлений (`npm run check:fix`, `npx prettier --write`, `npx eslint --fix`) снова запускать `npm run check`.
- **Тесты** проверяют поведение (запускают код), а не текст исходников.

## 3. Документация

- При изменении архитектуры, механик, правил интерфейса или состава файлов обновлять README и нужный документ в `docs/`; при изменении интерфейса партии — `docs/game-ui.md`.
- В AGENTS — только правила и подводные камни, без пересказа кода и описания поведения. Имена функций, классов и конкретные значения — только если без них правило непонятно. Подробности реализации — в комментариях к коду.

## 4. Код и модули

- Единственная точка входа — `js/main.js`, модули связаны явными `import`/`export`, глобальных переменных нет (кроме `firebase` из CDN).
- Импорты только через алиасы `#js/*` и `#assets/*`; относительные пути запрещены (ловит ESLint).
- Состояние партии — объект `state` из `js/game.js`: другие модули меняют его поля, а не переприсваивают импорт.
- Изображения подключаются импортами; JSON колоды из `resources/` грузится через `fetch()` и копируется в сборку как есть.
- `build/` генерирует Vite: не редактировать и не коммитить.
- Установка зависимостей — только `npm ci`; при их изменении коммитить и `package.json`, и `package-lock.json`.
- Настройка сборки не повод менять HTML-структуру, стили, анимации или игровую логику. Визуальные изменения — только по отдельному запросу.

## 5. Графика и адаптивность

- Исходные изображения в `assets/images/` никогда не перезаписывать оптимизированными версиями; оптимизированные копии делает сборка, руками их не готовить. Не снижать качество изображений ради размера файла.
- `index.html` заранее грузит фоны и логотипы (preload); не убирать эти подсказки без сопоставимой замены.
- Интерфейс оптимизирован под Retina: растровые изображения — не меньше двойного CSS-размера; размеры, от которых зависит положение мелких элементов (точки на поле), держать целыми и чётными, чтобы они не съезжали на полпикселя.
- Граница телефона — 760px. Ширина влияет только на раскладку; управление и подсказки зависят от способа ввода.

### Иконки

- **Основной набор — [Tabler Icons](https://tabler.io/icons)**, npm-пакет `@tabler/icons` (MIT, версия закреплена в `package.json`). По умолчанию стиль outline (`outline/`); filled (`filled/`) — когда задаче нужна залитая иконка, например для выбранного состояния. Иконки берутся из пакета как есть, без копирования в репозиторий и правок рисунка; толщину линии под размер подгоняет сборка (см. «Толщина линии»). Своя иконка — только если в Tabler подходящей нет (как иконки режимов игры): SVG-файл в `assets/icons/` на холсте `viewBox="0 0 64 64"`.
- **Подключение — компонент `.icon`** (`css/components/icon.css`): у каждой иконки модификатор `.icon--<имя>` с `--icon-image: url('@tabler-size/24/<стиль>/<имя-в-tabler>.svg')` (своя — `url('../../assets/icons/<файл>.svg')`), в разметке — `<span class="icon icon--<имя>" aria-hidden="true"></span>`. Модификаторы рассчитаны на размер по умолчанию 24px. Если иконка стоит в другом размере, блок задаёт себе и `--icon-size`, и `--icon-image` с тем же размером в пути (`--icon-size: 16px; --icon-image: url('@tabler-size/16/outline/x.svg')`), а в разметке остаётся `<span class="icon">`. Путь `@tabler/icons/...` в CSS напрямую не использовать. Файл служит CSS `mask`, а цвет даёт `background-color: currentColor`. Vite встраивает в CSS только иконки, на которые есть ссылки, поэтому остальной набор в сборку и в браузер не попадает. Не импортировать пакет целиком, не встраивать SVG в HTML и не грузить иконки с CDN или других сайтов.
- **Без npm и среды запуска (чат ChatGPT):**
    1. Найти иконку поиском на [tabler.io/icons](https://tabler.io/icons) и выбрать стиль (outline или filled); имя — последняя часть адреса страницы иконки `https://tabler.io/icons/icon/<имя>` (например, `x`, `settings`, `question-mark`).
    2. Проверить, что файл есть в закреплённой версии: `https://github.com/tabler/tabler-icons/blob/v<версия из package.json>/icons/<стиль>/<имя>.svg`. Иконки из более новых версий может не быть, а filled-версия есть не у каждой иконки.
    3. Добавить модификатор в `css/components/icon.css` по образцу соседних и элемент в разметку, как описано выше; в пути `@tabler-size/<размер>/<стиль>/<имя>.svg` размер — тот, в котором иконка видна на странице (её `--icon-size`, по умолчанию 24). Сам SVG в репозиторий не копировать.
    4. Опечатку в имени или размер не кратный 8 ловит сборка и её тесты: дождаться Frontend checks.
- **Второй цвет** — отдельный файл-маска того же холста, наложенный псевдоэлементом `::after` только в модификаторе этой иконки: `::after` без своей маски закрашивает весь квадрат. Цвет — токен в `--icon-detail-color`.
- **Растровые иконки — только по просьбе пользователя**, например если он прислал найденную иконку. Допустимы форматы без потерь: PNG или WebP lossless. JPEG и другие форматы с потерями не принимать: сжатие даёт артефакты по контурам, у JPEG нет прозрачности, а при масштабировании и на Retina дефекты становятся заметнее. В этом случае объяснить пользователю причину и попросить прислать PNG, lossless WebP или SVG. Растровая иконка — не меньше 3x от CSS-размера, на квадратном холсте.
- **Квадрат.** Холст иконки квадратный, у всех иконок одного набора — один размер холста: у Tabler 24, у своих 64.
- **Прозрачный фон.** Непрозрачен только сам рисунок: никаких подложек, заливки холста или белого фона под иконкой, в том числе у растровых иконок. В маске любой непрозрачный пиксель окрашивается, поэтому фон превратится в цветной квадрат.
- **Поля внутри холста — часть рисунка.** Отступ от краёв нужен только для оптического выравнивания: круг рисуется крупнее квадрата, чтобы выглядеть одного размера с ним, узкая фигура центрируется по визуальному центру. Иконки одного набора стоят рядом ровно и с одинаковым видимым весом без подгонки снаружи.
- **Размер, отступы и выравнивание задаёт внешний код.** Размер — переменная `--icon-size`, которую ставит блок, зазор до текста — `gap` родителя, вертикальное выравнивание — флекс или грид родителя. В самой иконке нет `margin`, а поля холста не используются как отступ от текста.
- **Цвет — цвет текста родителя** (маска с `currentColor`), без зашитых цветов. Иконка перекрашивается вместе с родителем, в том числе в тёмной теме.
- **Толщина линии — 1,5 px на экране у всех outline-иконок.** Tabler рисует линию в 2 единицы на холсте 24, а маска масштабирует её вместе с иконкой, поэтому плагин сборки (`tools/vite-tabler-size.mjs`) по размеру из пути `@tabler-size/<размер>/...` делает копию иконки с толщиной `1,5 × 24 / размер`. Размер в пути должен совпадать с `--icon-size`, иначе линия выйдет толще или тоньше.
- **Чёткость.** В своих иконках прямые линии и края лежат на целых единицах `viewBox`. Размер иконки кратен 8 px (16, 24, 32, 48, 64); другие размеры плагин сборки не принимает.

## 6. Интерфейс

### Единое поведение

- Мышь, касание и клавиатура приводят к одним и тем же состояниям разными событиями; никаких особых веток под отдельный флоу, тему или устройство, кроме описанных в `docs/game-ui.md` осознанных различий.
- Одиночная игра и онлайн ведут себя и выглядят одинаково.

### Паттерны UX

- Выбор из нескольких вариантов с клавиатуры — нативная группа радиокнопок (видимая или скрытая `visually-hidden`), а не свои обработчики стрелок.
- Модальное окно при открытии переносит фокус внутрь (на первую кнопку или «Закрыть»), иначе Tab ходит по странице под ним.
- Модальные окна открываются и закрываются через `js/modal.js`: он же запирает прокрутку страницы, пока окно открыто, — колесо и свайп поверх окна не должны прокручивать страницу под ним.
- Всплывающие окна, меню и панели закрываются по Esc.
- Меню действий — компонент `menu` (`css/components/menu.css` и `createMenu` из `js/menu.js`), а не своя разметка и обработчики в блоке. Блок главного экрана называется `home`, чтобы не путаться с ним.
- Полосы прокрутки — системные: не подключать JS-библиотеки своих полос прокрутки и не оформлять полосы через `::-webkit-scrollbar`. Чтобы полоса не вылезала за скругления, в модальном окне прокручивается внутренний блок, отступающий от верхнего и нижнего края окна. У поля и руки на телефоне полосы скрыты (`scrollbar-width: none` и `::-webkit-scrollbar { display: none }` для старого Safari): прокрутка остаётся колесом, перетаскиванием и пальцем.
- Закрытое окно, меню или панель возвращает фокус на элемент, который его открыл (`js/focus-return.js`).
    - Возврат выполняется, только если фокус был внутри окна или потерян; если пользователь уже увёл фокус наружу, он остаётся там.
    - Открывший элемент передаётся явно, а не берётся из `document.activeElement`: Safari не фокусирует кнопку по клику. Если он перерисовывается, пока окно открыто, передаётся функция, которая найдёт его заново.
- Разовые сообщения о результате действия и все ошибки действий и сети — только через `snackbar(text, kind)`, без точки в конце. Постоянные инструкции, подсказки и текущее состояние (строка статуса, таймер хода) остаются на странице.

### Интерфейс партии: подводные камни

- Карты в руке и положения на поле — нативные группы радиокнопок (скрытые `input type="radio"` внутри `label`).
    - Свою логику обхода стрелками не писать: стрелки отмечают кнопки нативно, а код только реагирует на `change` и решает, куда поставить фокус при входе в группу.
    - Не подменять нативное поведение стрелок: без отмеченной кнопки → отмечает следующую после элемента с фокусом, а не его самого (его отмечают Enter или пробел).
    - Пока выбирается положение, фокус всегда в группе положений: наведение мыши переносит фокус на радиокнопку наведённого положения, не отмечая её, чтобы стрелки шли от него.
    - Кольца фокуса у карт нет — его роль играют подсветка и рамка.
- Рука перерисовывается на месте (элементы оставшихся карт не пересоздаются): подъём и полоска анимируются переходами, а пересоздание ломает переходы, `:hover` (карта под курсором моргает) и фокус.
- Рамка карты не меняет размер карты и не сдвигает сетку клеток.
    - На поле рамка лежит на целых пикселях: первая строка и столбец карты плюс пиксель за последними. Так общий край соседних карт рисуется на одних и тех же пикселях. Линия толщиной 1px, центрированная на краю, на экране 1x размазывается на два полупрозрачных пикселя, и на стыках карт цвет меняется.
    - У превью полупрозрачны только клетки, рамка остаётся непрозрачной. Пунктир превью лежит целиком внутри карты: иначе его правый и нижний края выходят за карту и в разрывах видно поле.
    - В руке рамка — `outline`. `border` для рамок не использовать — он сдвигает сетку клеток.
    - Осветление стен — цветом, не `filter` (он стирает линии клеток).
- Кнопки «Отмена» / «Поставить» не прятать медиазапросом по ширине: на планшете в альбомном режиме и в «версии для ПК» без них карту было не поставить. Видимость панели зависит только от вида превью.
- Режим выбора положения не хранится отдельно, а выводится из наличия превью: иначе наведённое превью и стрелки, меняющие карту, расходятся.
- Наведение двигает только превью, без перерисовки поля.
    - Наведением считается лишь реальный сдвиг указателя без нажатых кнопок: Chrome повторяет `pointermove` после перерисовки, и неподвижный курсор не должен отбирать превью у стрелок.
    - Движение мыши с зажатой кнопкой не должно очищать превью: небольшое смещение во время клика не должно превращать размещение в повторный выбор позиции.
- Камера — свой контекст наложения (`z-index`): иначе точки положений с их `z-index` всплывают над панелью масштаба и панелью «Отмена» / «Поставить».
- Точки на поле декоративные: фокус получает скрытая радиогруппа положений. Нажатие на поле не забирает фокус.
- Кнопка «?» стоит в DOM после руки, чтобы Tab доходил до неё после карт; на строку заголовка её возвращает грид.
- Текст подсказок «?» выбирается по способу ввода в момент открытия, а не по ширине.
- Значки «−» и «+» у масштаба — иконки, а не символы шрифта: глифы сидят не по центру строки, и в каждом системном шрифте по-разному.
- Высоты экрана партии задаёт флекс, а не формулы `calc(100svh - Npx)`: страница — колонка во всю высоту окна, поле растягивается на остаток. Камера изолирует свой размер (`contain: size`), иначе огромное поле внутри неё растягивает экран выше окна.
- Шторка на телефоне меняет высоту не только вместе с окном (таймер хода, цель обучения), поэтому камера следит за своим размером: центр вида сохраняется сразу, а поле перерисовывается, когда размер устоялся. Временные кнопки поверх поля геометрию не меняют.
- Скрытая кнопка «Сбросить карты» не занимает места вместе со своим отступом.
- Фокус в руку ставится без прокрутки страницы. Если перерисовка спрятала элемент с фокусом, фокус возвращается в руку.
- В онлайне статус «Твой ход» не затирает подсказку выбора положения.
- Анимация новой карты не должна перезапускаться при перерисовке поля.

### Пользовательские испытания

- Редактор только на десктопе; мобильный интерфейс редактором не расширять без отдельного запроса.
- Редактор открывает сам экран одиночной партии (`#play`, `#camera`, `#board`, игровой рендерер, камера, масштаб, `.game__layout`), а не отдельное окно с копией поля. Не создавать отдельный DOM-рендер поля или собственный расчёт точек: проверка и точки размещения — тот же алгоритм, что в игре.
- Клики редактора по карте и точке не запускают игровой ход, не меняют статистику и не завершают партию; состояние игры до открытия редактора восстанавливается при выходе.
- В интерфейсе редактора — подписи элементов и важные сообщения о состоянии, без пояснений об очевидных действиях или расположении элементов.
- Пользовательские названия и описания выводятся только как текст, не HTML.
- Пустые массивы Firebase могут прийти как `null`: нормализовать в пустые списки.
- Правила Firebase Realtime Database меняются в `database.rules.json`, а не в README или документах; после изменения файл целиком переносится в консоль Firebase. Файл — полный набор правил: ветку, которой в нём нет, консоль удалит. Не должно быть более широкого родительского `.write`, обходящего правила `rooms` и `challenges`. Комнату читает только её игрок: код входа сначала записывает игрока, потом читает комнату. Кнопки редактирования и удаления в интерфейсе показываются только владельцу, но защита — серверные правила.

## 7. Стили (дизайн-система)

### Структура и слои

- Слои: `@layer tokens, base, components, blocks, utilities;` (объявлены в `css/tokens.css`). Каждый файл целиком лежит в своём слое, поэтому специфичность между слоями не важна.
- `css/tokens.css` — единственное место с «сырыми» значениями: цвета, шрифты, размеры, отступы, радиусы, тени, z-index. Тёмная тема — только переопределение переменных в `.dark-theme` в этом же файле.
- `css/base.css` — сброс и умолчания. Селекторы по тегам разрешены только здесь.
- `css/components/` — переиспользуемые компоненты, `css/blocks/` — блоки экранов, `css/utilities.css` — `.hidden`, `.visually-hidden`, уменьшение анимаций.
- Новый файл стилей подключается в `index.html` в порядке: tokens → base → components → blocks → utilities.

### Правила, готовые к CSS-модулям

- Один блок — один файл, плоский BEM: `.block`, `.block__element`, `.block--modifier`. Файл стилизует только свои классы.
- Запрещены `!important`, селекторы по ID и селекторы с классами чужого блока. Композиция — несколько классов на одном элементе (`class="card card--glass home__card"`).
- Два модуля на одном элементе не объявляют одно и то же свойство. Блок настраивает компонент через его публичные переменные (`--card-padding`, `--hand-card-cell` и т. п.); компонент читает их с фолбэком и сам не объявляет.
- Медиазапросы лежат в файле своего блока.
- Анимации (`@keyframes`) называются с префиксом блока: `board-tile-drop`, `end-screen-pop`.
- Для модальных окон не анимировать `backdrop-filter`/`filter`: радиус размытия держать статичным и умеренным, а проявление слоя выполнять через `opacity`; содержимое анимировать только через `opacity` и `transform`. Длительность открытия и закрытия держать короткой и согласованной с JS-таймером закрытия.

### JS и классы

- JS находит элементы по `id` и `data-*`, а не по стилевым классам.
- Состояние — через модификаторы БЭМ и `.hidden`. Инлайновые цвета и `style.display` запрещены; инлайн допустим только для вычисляемой геометрии (позиции и размеры на поле) и случайных параметров конфетти.

### Цвета

- Только переменные из `tokens.css`. Близкие, неразличимые на глаз оттенки сводятся в один токен.
- Используем семантические токены (`--color-text*`, `--color-surface*`, `--color-border*`, `--color-control*`, `--color-primary*`, `--color-accent*`, `--color-success*`, `--color-danger*` и т. п.), а не произвольные.
- Фон диалогов, всплывающих панелей и меню непрозрачный — `--color-surface-dialog`. Полупрозрачные поверхности остаются только у плашек поля и боковой панели в игре.

### Отступы и размеры

- Все отступы, зазоры и размеры контролов кратны 4px (`--space-*`). Значения не из шкалы допустимы только для геометрии иллюстраций и анимаций.
- Иерархия: чем выше уровень или сильнее различие между элементами, тем больше отступ. Внутри элемента — 4–8, между элементами группы — 8–12, между группами внутри карточки и между карточками — 16–24, поля страницы — 16–56.
- Радиусы: 4 (карты в руке) / 8 / 12 / 16 / 20 / 28 / `full`. Высоты контролов: 36 / 44 / 52.

### Типографика

- Шкала: 12, 14, 15 (базовый текст), 16, 18, 20, 24, `--text-display` для финального экрана. Минимум — 12px, там, где хватает места, — 14px. Не мельчить шрифт ради вмещения — переносить строки или менять формулировку.
- Шрифты: `--font-sans` (системный) для текста, `--font-serif` (Merriweather 700) для заголовков, `--font-mono` для кода комнаты.
- `letter-spacing` используется только у кикера «Карточная игра · 1–4 игрока». Больше нигде.
- В HTML текст пишется в обычном регистре (с большой буквы), капс — только через CSS.
- Новый заголовок или подпись берут существующую текстовую роль (заголовок, подзаголовок, подпись, заголовок пункта, кикер), а не собственные стили.

## 8. Локальный сервер и браузерные проверки

- Для UI-задач агент с терминалом сам запускает `npm run dev:local` (только `127.0.0.1`, фиксированный порт 3000), если `http://localhost:3000` ещё не отвечает, и оставляет его запущенным между задачами. Если сервер уже работает, использовать его. Второй Vite не запускать: `server.open: true` открывает вкладку в браузере пользователя при каждом запуске. Для проверки сборки — `vite preview --open false`.
- После проверок Playwright удалять `.playwright-mcp/`.
- В headless-браузере `:hover` ненадёжен — состояние проверять по классам и элементам, а не по вычисленным стилям наведения. Касание проверять в контексте с `hasTouch`, а не кликом мыши в узком окне.
- Временные скрипты и скриншоты класть в `.tmp/` в проекте (игнорируется Git, ESLint и Prettier), а не в системный `/tmp`; скриншоты проверок не удалять.

## 10. Нативные приложения Tauri 2

- Нативный frontend обслуживается протоколом `bandito://` со встроенной сборкой как fallback. Не переводить приложение на удалённый URL и не убирать встроенный fallback.
- Нативная оболочка — в `src-tauri/`; не переносить игровую логику из `js/` в Rust без отдельной необходимости.
- Закрытый ключ OTA (`OTA_SIGNING_PRIVATE_KEY`) и Android keystore никогда не коммитить и не выводить в логи.
- OTA обновляет только веб-ресурсы. При добавлении или изменении native API повышать версию приложения и `min_app_version` в манифесте, сначала выпускать нативную сборку, затем OTA: web-код не должен вызывать native API, которого нет в минимальной поддерживаемой сборке.
- Скрипт `tauri` в `package.json` не удалять: сгенерированный Android Gradle-плагин вызывает `npm run tauri`, без него все Android ABI падают с `Missing script: "tauri"`.
- Сгенерированные иконки (PNG/ICO/ICNS), `src-tauri/gen/` и `src-tauri/target/` не коммитить.
- При изменении Firebase-интеграции синхронизировать CSP в `src-tauri/tauri.conf.json`: только нужные Google Fonts, Firebase SDK, WebSocket Realtime Database и Firebase Auth.
- После изменения нативной части проверять desktop и Android сборки ручным запуском `Build Bandito apps`.
