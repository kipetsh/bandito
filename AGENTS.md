# AGENTS.md

## Сводка по проекту

Bandito — карточная игра (адаптация настольной игры Bandido от Helvetiq) на HTML5, Vanilla JS и CSS. Веб-версия собирается Vite и публикуется на GitHub Pages; настольные и мобильные сборки используют Tauri 2 и общую веб-кодовую базу. Поддерживает одиночный режим (2, 5, 6 выходов) и кооперативный онлайн-мультиплеер до 4 игроков через Firebase Realtime Database.

## Обязательное правило: ESLint и Prettier

Перед написанием или изменением кода **обязательно изучить и соблюдать действующие конфиги проекта**: `eslint.config.mjs`, `.prettierrc.json` и `.prettierignore`. Не полагаться на личный стиль, память или настройки редактора. Код сразу писать в соответствии с этими правилами; перед проверкой форматировать все затронутые файлы через Prettier с учётом правил проекта. Не отключать, не ослаблять и не обходить правила ESLint/Prettier ради прохождения проверки без отдельной обоснованной необходимости. Исключения из `.prettierignore` соблюдать: не форматировать игнорируемые файлы целиком, если задача не требует их изменения; при точечном изменении форматировать только нужный участок безопасным способом.

**Код сразу писать по правилам проекта:** соблюдать ESLint и Prettier, а перед отправкой форматировать затронутые файлы. Обычный агент с локальным клоном до отправки запускает `npm run check`. ChatGPT с GitHub Plugin без локального клона вносит изменения непосредственно в `main`, затем проверяет тот же SHA через GitHub Actions.

## Ключевые соглашения и правила работы

### 1. Правило коммитов

- **Единая рабочая ветка — `main`.** Все задачи по приложению выполняются непосредственно в `main`. Не создавать постоянные feature-ветки и отдельные ветки для проверок; временная ветка допустима только если её явно запросил пользователь или без неё технически невозможно завершить перенос.
- **Коммитить только явно выбранные файлы:** добавлять в индекс только целевые пути. Запрещены слепые команды `git add .`, `git add -A` и `git commit -a`.
- **Один цикл проверок на одну задачу:** сначала выполнить весь согласованный объём задачи целиком — все пункты плана, идеи и связанные правки. Затем собрать изменения в один логический набор, отформатировать все затронутые файлы и запустить проверки один раз в конце. Не запускать проверки после каждого промежуточного изменения или коммита. Если по техническим причинам нужны несколько коммитов, подготовить их все до отправки и отправить одной операцией (одним push), чтобы CI проверил итоговое состояние задачи, а не каждый промежуточный коммит. Не разбивать одну задачу на серию отдельных push только ради фиксации прогресса.
- **Обычный режим разработки с локальным клоном:** после каждой логически завершённой группы изменений форматировать затронутые файлы и запускать `npm run check`; для полной проверки проекта — `npm run check && npm run test`. Не отправлять изменения, пока обязательные локальные проверки не завершились успешно. Исключение — специальный publication-first процесс ChatGPT + GitHub Plugin из раздела 6.
- **Специальный режим ChatGPT + GitHub Plugin:** если у ChatGPT нет прямого доступа к терминалу клона, применять отдельный процесс из раздела 6. Этот вариант предназначен только для чата ChatGPT с GitHub Plugin, а не для любого агента.
- **Никаких заявлений о проверке без фактического запуска:** указывать, где именно прошли проверки — в терминале клона, в GitHub Actions на точном SHA проверочной ветки или в GitHub Actions.

### 2. Синхронизация документации

- При любых изменениях архитектуры, механик, правил интерфейса или состава файлов **всегда обновлять `README.md` и `AGENTS.md`**, сохраняя их в актуальном состоянии.
- `AGENTS.md` хранит решения, правила и подводные камни, а не пересказ кода: имена функций, классов и конкретные значения пишем, только если без них правило непонятно. Подробности реализации — в комментариях к коду.

### 3. Графика и адаптивность

- **Сохранение оригиналов:** исходные качественные изображения всегда хранятся в проекте (`assets/images/`) и никогда не перезаписываются оптимизированными версиями.
- **Оптимизированные копии в интерфейсе:** в игру попадают только оптимизированные копии — их делает сборка (WebP, ограничение размера), руками не готовим.
- **Иконки режимов и Retina:** визуальный размер измеряем по непустой области изображения, а не по исходному холсту. Для иконок одиночной игры и мультиплеера сохраняем прежние размеры SVG: 64 × 64 CSS px для обеих иконок, с одинаковой фиксированной шириной контейнера и одинаковым зазором до текста (16 px на широких экранах); изображение мультиплеера сохраняет исходные пропорции внутри контейнера. Сборка автоматически обрезает прозрачные поля, сохраняет пропорции и создаёт сжатые WebP-копии с плотностью 3x (192 × 192 и 192 × 178 px); исходники в `assets/images/` не изменяются. Не увеличивать CSS-контейнер ради компенсации пустых полей внутри файла.
- **Retina и экраны:** игра должна быть оптимизирована под экраны Retina (High-DPI / @2x), графика и элементы поля не должны размываться. Размеры, от которых зависит положение мелких элементов (точки на поле), держим целыми и чётными, чтобы они не съезжали на полпикселя.
- **Мобильные и десктопные экраны:** интерфейс, камера поля, перетаскивание и управление картами должны одинаково гладко и удобно работать как на смартфонах/планшетах, так и на десктопе. Граница телефона — 760px: на узком экране боковая панель партии становится нижней шторкой, базовая клетка поля меньше.
    - Ширина влияет только на раскладку; управление и подсказки зависят от способа ввода (см. [docs/game-ui.md](docs/game-ui.md)).

### 4. Игровые правила и интерфейс партии

#### Единое поведение

- Мышь, касание и клавиатура приводят к одним и тем же состояниям разными событиями; никаких особых веток под отдельный флоу, тему или устройство, кроме перечисленных ниже осознанных различий.
- Одиночная игра и онлайн ведут себя и выглядят одинаково (старт, выбор, ход, рука, поле).

#### Паттерны UX

- Выбор из нескольких вариантов с клавиатуры — нативная группа радиокнопок (видимая или скрытая `visually-hidden`), а не свои обработчики стрелок.
- Модальное окно при открытии переносит фокус внутрь (на первую кнопку или «Закрыть»), иначе Tab ходит по странице под ним.
- Модальные окна открываются и закрываются через `js/modal.js`: он же запирает прокрутку страницы, пока окно открыто, — колесо и свайп поверх окна не должны прокручивать страницу под ним.
- Всплывающие окна, меню и панели закрываются по Esc.
- Полосы прокрутки — системные: не подключать JS-библиотеки своих полос прокрутки и не оформлять полосы через `::-webkit-scrollbar`. Чтобы полоса не вылезала за скругления, в модальном окне прокручивается внутренний блок, отступающий от верхнего и нижнего края окна. У поля и руки на телефоне полосы скрыты (`scrollbar-width: none` и `::-webkit-scrollbar { display: none }` для старого Safari): прокрутка остаётся колесом, перетаскиванием и пальцем.
- Закрытое окно, меню или панель возвращает фокус на элемент, который его открыл (`js/focus-return.js`).
    - Возврат выполняется, только если фокус был внутри окна или потерян; если пользователь уже увёл фокус наружу, он остаётся там.
    - Открывший элемент передаётся явно, а не берётся из `document.activeElement`: Safari не фокусирует кнопку по клику. Если он перерисовывается, пока окно открыто, передаётся функция, которая найдёт его заново.

#### Интерфейс партии

Поведение руки, выбора положения, отмены, фокуса, поля, камеры и подсказок описано в [docs/game-ui.md](docs/game-ui.md); при изменении интерфейса партии обновлять этот документ. Ниже — только правила реализации и подводные камни.

- Карты в руке и положения на поле — нативные группы радиокнопок (скрытые `input type="radio"` внутри `label`).
    - Свою логику обхода стрелками не писать: стрелки отмечают кнопки нативно, а код только реагирует на `change` (выбор карты, показ превью) и решает, куда поставить фокус при входе в группу.
    - Не подменять нативное поведение стрелок: без отмеченной кнопки → отмечает следующую после элемента с фокусом, а не его самого (его отмечают Enter или пробел).
    - Пока выбирается положение, фокус всегда в группе положений: наведение мыши переносит фокус на радиокнопку наведённого положения, не отмечая её, чтобы стрелки шли от него.
    - Кольца фокуса у карт нет — его роль играют подсветка и рамка.
- Рука перерисовывается на месте (элементы оставшихся карт не пересоздаются): подъём и полоска анимируются переходами, а пересоздание ломает переходы, `:hover` (карта под курсором моргает) и фокус.
- Рамка карты не меняет размер карты и не сдвигает сетку клеток.
    - На поле рамка лежит на целых пикселях: первая строка и столбец карты плюс пиксель за последними. Так общий край соседних карт рисуется на одних и тех же пикселях. Линия толщиной 1px, центрированная на краю, на экране 1x размазывается на два полупрозрачных пикселя, и на стыках карт цвет меняется.
    - У превью полупрозрачны только клетки, рамка остаётся непрозрачной. Пунктир превью лежит целиком внутри карты: иначе его правый и нижний края выходят за карту и в разрывах видно поле.
    - В руке рамка — `outline`, рамку выбранной и указанной карты не утолщаем.
    - `border` для рамок не использовать — он сдвигает сетку клеток.
    - Осветление стен — цветом, не `filter` (он стирает линии клеток).
- Кнопки «Отмена» / «Поставить» не прятать медиазапросом по ширине: на планшете в альбомном режиме и в «версии для ПК» без них карту было не поставить. Видимость панели зависит только от вида превью.
- Режим выбора положения не хранится отдельно, а выводится из наличия превью: иначе наведённое превью и стрелки, меняющие карту, расходятся.
- Наведение двигает только превью, без перерисовки поля.
    - Наведением считается лишь реальный сдвиг указателя без нажатых кнопок: Chrome повторяет `pointermove` после перерисовки, и неподвижный курсор не должен отбирать превью у стрелок.
    - Движение мыши с зажатой кнопкой не должно очищать превью: небольшое смещение во время клика не должно превращать размещение в повторный выбор позиции.
- Камера — свой контекст наложения (`z-index`): иначе точки положений с их `z-index` всплывают над панелью масштаба и панелью «Отмена» / «Поставить».
- Точки на поле декоративные: фокус получает скрытая радиогруппа положений. Нажатие на поле не забирает фокус.
- Кнопка «?» стоит в DOM после руки, чтобы Tab доходил до неё после карт; на строку заголовка её возвращает грид.
- Текст подсказок «?» (модальное окно) выбирается по способу ввода в момент открытия, а не по ширине. Главное в нём — самый простой способ хода, клавиши — отдельным блоком.
- Значки «−» и «+» у масштаба рисуются полосками, а не символами шрифта: глифы сидят не по центру строки, и в каждом системном шрифте по-разному.
- На телефоне экран партии — колонка во всю высоту окна: заголовок, поле на всё оставшееся место и боковая панель как нижняя шторка. Шторка меняет высоту не только вместе с окном: таймер хода в онлайне, цель обучения. Поэтому камера следит за своим размером: центр вида сохраняется сразу, а поле перерисовывается, когда размер устоялся. Временные кнопки поверх поля геометрию не меняют.
- Высоты экрана партии задаёт флекс, а не формулы `calc(100svh - Npx)`: страница — колонка во всю высоту окна, поле растягивается на остаток. Камера изолирует свой размер (`contain: size`), иначе огромное поле внутри неё растягивает экран выше окна.
- Кнопка «Сбросить карты», пока скрыта, не занимает места вместе со своим отступом.
    - На десктопе, появляясь, она выезжает под рукой и сдвигает подсказку ниже.
    - На телефоне она висит поверх нижней части поля по центру, как панель «Отмена» / «Поставить», и поднимает кнопки масштаба, чтобы не наползать на них; размеры поля и шторки не меняются. Широкая панель «Отмена» / «Поставить» кнопки масштаба просто закрывает.
- Фокус в руку ставится без прокрутки страницы. Если перерисовка спрятала элемент с фокусом, фокус возвращается в руку.
- В онлайне статус «Твой ход» не затирает подсказку выбора положения.
- Поле — объединение игровой области и текущего вида камеры, поэтому прокрутка есть только для части, выходящей за вид.
- Анимация новой карты не должна перезапускаться при перерисовке поля.
- Размер точки положения растёт с зумом чётными шагами, чтобы она не съезжала на полпикселя.

#### Правила игры

- **Колода и сброс:** сброшенные карты уходят под низ колоды, взятие — всегда сверху. Сброс разрешён только при отсутствии доступных ходов.
- **Одиночная игра из лобби:** кнопки одиночных режимов доступны рядом с лобби кооператива, поэтому старт одиночной партии сначала выходит из комнаты — иначе карты в руке остаются заблокированными.
- **Таймер хода:** истечение 60 секунд в онлайне только передаёт очередь, карты в руке сохраняются.

#### Пользовательские испытания

- Редактор и публикация пользовательских испытаний доступны только на десктопе; мобильный интерфейс игры не расширять редактором без отдельного запроса. Редактор открывает сам экран одиночной партии, а не отдельное окно с копией поля: используются существующие `#play`, `#camera`, `#board`, игровой рендерер, камера, масштаб и раскладка `.game__layout`. В правой игровой панели временно скрываются метрики и обычная рука, вместо них показываются инструменты редактора, выбранная карта, стартовая рука и колода добора. Создание и библиотека открываются отдельными кнопками главного меню. В интерфейсе оставлять подписи элементов и важные сообщения о состоянии, но не добавлять пояснения об очевидных действиях или расположении элементов.
- Стартовая карта обязательна и определяется сложностью: 2 выхода — карта 75, 5 выходов — карта 72, 6 выходов — карта 71. В редакторе нельзя перемещать или удалять стартовую карту.
- Раскладка поля хранится как идентификаторы карт, координаты и повороты. Проверка размещения использует тот же алгоритм совпадения тоннелей и запрета пересечений, что и обычная игра.
- При добавлении карты редактор использует штатные точки игрового поля и тот же расчёт допустимых размещений и поворотов, что и соло-режим; клик по точке устанавливает карту. Ориентация новой карты выбирается цветной точкой; отдельной кнопки поворота нет. Уже установленную карту можно выделить кликом непосредственно на поле и удалить кнопкой панели; отдельная кнопка выделения не нужна. Стартовую карту нельзя перемещать, поворачивать или удалять. Каталог карт показывает только увеличенные изображения без подписей с ID; превью карт в каталоге и колоды должны занимать больше свободного места в своих контейнерах, сохраняя пропорции матрицы. В панели редактора остаётся компактная кнопка «Изменить»; кнопка «Очистить колоду» показывается справа от «Готово» внизу открытого каталога колоды. Колоду добора можно настроить или полностью очистить. После выхода из редактора состояние обычной игры восстанавливается.
- Для публикации пользовательского испытания обязательно только непустое название; заполнение стартовой руки и проверка раскладки не блокируют публикацию. Стартовая рука содержит от нуля до трёх выбранных карт: пустые слоты не заполняются автоматически. После каждого хода рука пополняется из колоды до трёх карт, если в колоде достаточно карт. Пустые массивы Firebase Realtime Database могут возвращаться как `null`; редактор и запуск игры нормализуют такие значения в пустые списки.
- Режим редактирования не блокирует открытие раскладки из-за нарушений стыковки, пересечений, порядка стартовой карты или восстанавливаемых некорректных значений. При загрузке редактор нормализует координаты и повороты, переносит стартовую карту выбранной сложности на первое место, а при её отсутствии восстанавливает её; неизвестные карты пропускаются. Проверка правил игры остаётся обязательной при запуске. Текст пользовательских названий и описаний выводится только как текст, не HTML.
- Редактор сначала выполняет анонимный вход Firebase Authentication. Для `/challenges` правила разрешают чтение при `auth != null`; создание — только с `ownerUid === auth.uid`; обновление и удаление — только если существующая запись принадлежит `auth.uid`, а при обновлении `ownerUid` остаётся неизменным. Эти правила добавляются отдельной веткой, не заменяя правила `rooms`; не должно быть более широкого родительского `.write`, обходящего ограничение. В библиотеке кнопки редактирования и удаления показываются только владельцу; серверные правила остаются обязательной защитой.

### 5. Архитектура стилей (дизайн-система)

#### Структура и слои

- Слои: `@layer tokens, base, components, blocks, utilities;` (объявлены в `css/tokens.css`). Каждый файл целиком лежит в своём слое, поэтому специфичность между слоями не важна.
- `css/tokens.css` — единственное место с «сырыми» значениями: цвета, шрифты, размеры, отступы, радиусы, тени, z-index. Тёмная тема — только переопределение переменных в `.dark-theme` в этом же файле.
- `css/base.css` — сброс и умолчания. Селекторы по тегам разрешены только здесь.
- `css/components/` — переиспользуемые компоненты, `css/blocks/` — блоки экранов, `css/utilities.css` — `.hidden`, `.visually-hidden`, уменьшение анимаций.
- Новый файл стилей подключается в `index.html` в порядке: tokens → base → components → blocks → utilities.

#### Правила, готовые к CSS-модулям

- Один блок — один файл, плоский BEM: `.block`, `.block__element`, `.block--modifier`. Файл стилизует только свои классы.
- Запрещены `!important`, селекторы по ID и селекторы с классами чужого блока. Композиция — несколько классов на одном элементе (`class="card card--glass menu__card"`).
- Два модуля на одном элементе не объявляют одно и то же свойство. Блок настраивает компонент через его публичные переменные (`--card-padding`, `--hand-card-cell` и т. п.); компонент читает их с фолбэком и сам не объявляет.
- Медиазапросы лежат в файле своего блока.
- Анимации (`@keyframes`) называются с префиксом блока: `board-tile-drop`, `end-screen-pop`.
- Для модальных окон не анимировать `backdrop-filter`/`filter`: радиус размытия держать статичным и умеренным, а проявление слоя выполнять через `opacity`; содержимое анимировать только через `opacity` и `transform`. Длительность открытия и закрытия держать короткой и согласованной с JS-таймером закрытия.

#### JS и классы

- JS находит элементы по `id` и `data-*`, а не по стилевым классам.
- Состояние — через модификаторы БЭМ и `.hidden`. Инлайновые цвета и `style.display` запрещены; инлайн допустим только для вычисляемой геометрии (позиции и размеры на поле) и случайных параметров конфетти.
- **Снекбар:** разовые сообщения о результате действия (скопирован код, вышел из комнаты, отказ, ошибки сети) — только через `snackbar(text, kind)`; они исчезают сами. Все ошибки действий и сети показываются только снекбаром. Точку в конце сообщения снекбара не ставим. Постоянные инструкции, подсказки и текущее состояние (строка статуса, таймер хода) остаются на странице.

#### Цвета

- Только переменные из `tokens.css`. Близкие, неразличимые на глаз оттенки сводятся в один токен.
- Используем семантические токены (`--color-text*`, `--color-surface*`, `--color-border*`, `--color-control*`, `--color-primary*`, `--color-accent*`, `--color-success*`, `--color-danger*` и т. п.), а не произвольные.
- Фон диалогов, всплывающих панелей и меню непрозрачный — `--color-surface-dialog`. Полупрозрачные поверхности остаются только у плашек поля и боковой панели в игре.

#### Отступы и размеры

- Все отступы, зазоры и размеры контролов кратны 4px (`--space-*`). Значения не из шкалы допустимы только для геометрии иллюстраций и анимаций.
- Иерархия: чем выше уровень или сильнее различие между элементами, тем больше отступ. Внутри элемента — 4–8, между элементами группы — 8–12, между группами внутри карточки и между карточками — 16–24, поля страницы — 16–56.
- Радиусы: 4 (карты в руке) / 8 / 12 / 16 / 20 / 28 / `full`. Высоты контролов: 36 / 44 / 52.

#### Типографика

- Шкала: 12, 14, 15 (базовый текст), 16, 18, 20, 24, `--text-display` для финального экрана. Минимум — 12px, там, где хватает места, — 14px. Не мельчить шрифт ради вмещения — переносить строки или менять формулировку.
- Шрифты: `--font-sans` (системный) для текста, `--font-serif` (Merriweather 700) для заголовков, `--font-mono` для кода комнаты.
- `letter-spacing` используется только у кикера «Карточная игра · 1–4 игрока». Больше нигде.
- В HTML текст пишется в обычном регистре (с большой буквы), капс — только через CSS.
- Новый заголовок или подпись берут существующую текстовую роль (заголовок, подзаголовок, подпись, заголовок пункта, кикер), а не собственные стили.

### 6. Сборка, проверки и форматирование

- **Среда:** Node.js не ниже 22.12.0 (`.nvmrc`, `package.json`).
- **Установка:** только `npm ci`. `package-lock.json` хранится в репозитории; при изменении зависимостей коммитить и `package-lock.json`, и `package.json`.
- **Команды:** `npm run check` независимо запускает Prettier и ESLint и показывает результаты обоих инструментов, даже если один завершился с ошибкой. Оба инструмента должны выводить полный список найденных проблем, без намеренного ограничения количества диагностик. `npm run test` запускает исходные тесты, production-сборку и тесты результата сборки. `npm run build` отдельно создаёт production-сборку; `npm run test:build` проверяет уже собранную папку `build/`.
- **Автоисправления:** при редактировании сразу соблюдать правила ESLint и Prettier. Перед проверкой форматировать затронутые файлы. `npm run check:fix` выполняет автоисправление ESLint и форматирование проекта; для точечной работы допустимы `npx prettier --write <файлы>` и `npx eslint <файлы> --fix`. После автоисправлений обязательно повторно запускать `npm run check`.
- **Коммиты и проверки:** обычный агент с локальным клоном обязан форматировать затронутые файлы и запускать `npm run check` до отправки изменений; для полной проверки также запускать `npm run test`. ChatGPT с GitHub Plugin без локального терминала работает непосредственно с `main`, проверяет diff через GitHub и после push отслеживает соответствующие GitHub Actions. Не утверждать, что локальные команды запускались, если они фактически не запускались. Постоянные рабочие ветки для приложения не создавать: актуальный код хранится в `main`.
- **Единая инфраструктура:** общие инструменты и workflow находятся в основном репозитории, начиная с `main`: `package.json`, `package-lock.json`, `tools/check.mjs`, `.prettierignore`, `.github/workflows/check.yml`, `.github/workflows/deploy.yml` и этот раздел `AGENTS.md`. Проверочная ветка содержит только изменения приложения и документации по задаче, а не отдельную инфраструктуру для переноса.
- **Раздельные workflow:** `.github/workflows/deploy.yml` запускается при push в `main` и публикует GitHub Pages. `.github/workflows/check.yml` проверяет PR и тот же SHA после публикации. `.github/workflows/build-apps.yml` при push в `main` запускает frontend quality checks и OTA-публикацию; нативные сборки запускаются только вручную через `workflow_dispatch`. Старые workflow для веток `*-chatgpt-check` не являются частью штатного процесса разработки приложения.
- **Когда запускаются workflow:**
    - Push в `main`: сначала независимо запускается публикация (`npm ci`, `npm run build`, Pages Artifact, deploy). После завершения workflow публикации автоматически запускается `.github/workflows/check.yml` на том же SHA, даже если деплой завершился ошибкой. Публикация не зависит от результата проверок.
    - Любой pull request (независимо от целевой ветки): `.github/workflows/check.yml` запускает `npm ci`, `npm run check` и `npm run test:source`; Pages deployment не выполняется.
    - Ручной запуск `Build Bandito apps` из `main`: запускает quality checks и сборки Windows, macOS, Android; OTA не публикуется повторно.

- **Работа ChatGPT по GitHub Actions:** изучить конфиги форматирования и актуальный HEAD `main`, внести завершённый набор изменений в `main`, проверить diff и дождаться CI на точном SHA. Не заявлять о локальном запуске проверок. Если CI сообщает об ошибках, получить логи, исправить их в `main` отдельным коммитом и дождаться повторного результата. Код приложения не вести в отдельной постоянной ветке.
- **Ссылки на комнаты:** веб-мультиплеер использует URL `/<6-значный-код>` относительно базового пути приложения. Создание комнаты, вход по коду и выход из комнаты обновляют адрес через History API без перезагрузки. При открытии прямой ссылки `js/main.js` автоматически подключается к комнате. `tools/copy-static.mjs` создаёт `build/404.html` из той же production-страницы и добавляет динамический `<base>`, чтобы GitHub Pages корректно загружал ресурсы из project path. Не заменять fallback перенаправлением на главную; покрывать его и построение URL тестами. Нативный протокол `bandito://` не переписывать.
- **Выход сборки:** `build/` генерирует Vite, он игнорируется Git и не редактируется вручную. GitHub Pages публикует `build/`, созданную workflow `.github/workflows/deploy.yml` на push в `main`; публикация не ждёт ESLint, Prettier или тестов.
- **Модули:** единственная точка входа — `js/main.js`, модули связаны явными `import`/`export`, глобальных переменных нет (кроме `firebase` из CDN). Состояние партии — объект `state` из `js/game.js`; другие модули меняют его поля, а не переприсваивают импорт. Масштаб игрового поля хранится в `localStorage` под ключом `banditoZoom` как процент от базового размера клетки и восстанавливается при перезагрузке; при смене ширины экрана процент сохраняется.
- **Импорты только через алиасы** `#js/*` и `#assets/*` (subpath imports в `package.json`); относительные пути запрещены и ловятся ESLint.
- **Ресурсы:** изображения подключаются импортами и собираются Vite; JSON колоды из `resources/` копируется в сборку как есть, потому что грузится через `fetch()`. При сборке обычные изображения конвертируются в WebP, только если результат не больше исходника; исходники в `assets/images/` не меняются. Исключение — `solo-organic-circle` и `multiplayer-stars`: для них всегда создаются Retina WebP-файлы заданных размеров с фиксированными настройками качества. Не снижать качество ради того, чтобы результат оказался меньше уже оптимизированного оригинала; размер файла не является критерием успешной оптимизации этих иконок.
- **Preload:** `index.html` заранее грузит фоны и логотипы; не убирать эти подсказки без сопоставимой замены.
- **Pre-commit и CI:** перед коммитом `lint-staged` проверяет и форматирует staged-файлы. Проверки выполняются на pull request и после завершения публикации в `main`; frontend checks и OTA публикация также запускаются при push в `main`. Нативные сборки не запускаются на каждый push.
- **Prettier:** 4 пробела (JSON и YAML — 2), ширина 120, одинарные кавычки, LF. Legacy UI-файлы исключены из глобальной проверки, чтобы не плодить whitespace-only diff; staged-файлы форматируются всегда.
- **Тесты** проверяют поведение (запускают код), а не текст исходников.
- **Временные файлы:** временные скрипты и скриншоты кладём в `.tmp/` в проекте (игнорируется Git, ESLint и Prettier), а не в системный `/tmp`; скриншоты проверок после проверки не удаляем.
- **Браузерные проверки:** проверять на уже запущенном `npm run dev` (`http://localhost:3000`); второй Vite не запускать — в конфиге `server.open: true`, и каждый запуск открывает вкладку в браузере пользователя (если сервер не запущен — спросить или запускать с `--open false`, для сборки — `vite preview --open false`).
- **Локальный сервер для UI-задач:** при наличии локального клона и терминала агент сам запускает `npm run dev:local`, если сервер ещё не отвечает на `http://localhost:3000`; не просит пользователя напоминать или запускать его вручную. Если сервер уже работает, использует его и не поднимает второй. Оставляет сервер запущенным между итерациями и повторно использует его в следующих задачах. `npm run dev:local` привязывает Vite только к `127.0.0.1` и использует фиксированный порт 3000 (`strictPort`), а `npm run dev` остаётся командой для доступа из локальной сети. Этот шаг применим к агентам с локальным терминалом; GitHub-only чат без доступа к локальному процессу не заявляет, что localhost запущен. После проверок Playwright удалять `.playwright-mcp/`. В headless-браузере `:hover` ненадёжен — состояние проверять по классам и элементам, а не по вычисленным стилям наведения. Касание проверять в контексте с `hasTouch`, а не кликом мыши в узком окне.
- **Дизайн:** настройка сборки не повод менять HTML-структуру, стили, анимации или игровую логику. Визуальные изменения — только по отдельному запросу.
- **После правок:** форматировать затронутые файлы и запускать `npm run check`; для полной проверки проекта — `npm run check && npm run test`.

## Нативные приложения Tauri 2

- Нативный frontend обслуживается собственным протоколом `bandito://`: встроенная Vite-сборка остаётся резервной копией, а активная OTA-версия хранится в каталоге данных приложения. Не переводить приложение на удалённый URL и не убирать встроенный fallback.
- OTA обновляет только веб-ресурсы (HTML, CSS, JavaScript и данные/изображения). Rust-команды, Tauri, плагины, разрешения и конфигурация платформ обновляются только новой нативной сборкой.
- OTA-манифест и архив публикуются в GitHub Release с тегом `ota-latest`. Манифест подписывается Ed25519; клиент проверяет подпись закреплённым публичным ключом и SHA-256 архива до распаковки. Закрытый ключ хранится только в GitHub Actions Secret `OTA_SIGNING_PRIVATE_KEY`, в Base64 от PEM. Никогда не коммитить и не выводить его в логи.
- OTA-архив распаковывается во временную версионную папку с ограничениями размера, числа файлов и путей. После проверки архив помечается как подготовленный, а активируется только при следующем запуске — текущая игровая сессия не прерывается. Когда обновление готово, приложение показывает постоянную плашку с кнопкой перезапуска; используется полный restart нативного приложения, а не только reload WebView. Протокол проверяет незавершённый запуск до отдачи index.html и при сбое возвращает предыдущую версию; после успешного старта старые файлы удаляются.
- В манифесте обязателен `min_app_version`: не публиковать web-код, который вызывает native API, отсутствующий в минимальной поддерживаемой нативной сборке. При добавлении или изменении native API повышать версию приложения и `min_app_version`, сначала выпускать новую нативную сборку, затем публиковать OTA. Текущая минимальная версия для OTA-перезапуска — 0.1.1.
- Workflow `.github/workflows/build-apps.yml` запускает frontend quality checks и публикацию OTA при push в `main`. Дорогие сборки macOS, Windows и Android выполняются только при ручном запуске через `workflow_dispatch`. Параметры `build_apps` (по умолчанию true) и `publish_ota` (по умолчанию false) позволяют отдельно собрать приложения или опубликовать OTA. Если `OTA_SIGNING_PRIVATE_KEY` не задан, публикация OTA пропускается.
- `frontendDist` указывает на `bandito://localhost`; Rust-модуль `src-tauri/src/ota.rs` встраивает `build/` как offline fallback. Поэтому Tauri build должен запускать `npm run build` до компиляции Rust-кода.

- Веб-версия остаётся самостоятельной и продолжает публиковаться через существующий workflow GitHub Pages только из `main`.
- Нативная оболочка располагается в `src-tauri/`; не переносить игровую логику из `js/` в Rust без отдельной необходимости.
- Для разработки приложения использовать `npm run app:dev`; отдельный Vite-скрипт `dev:tauri` не открывает дополнительное окно браузера и фиксирует порт 3000.
- Production-сборка Tauri запускает существующий `npm run build` через `beforeBuildCommand`; каталог frontendDist — `build/`.
- Иконки платформ генерируются из исходного `src-tauri/icons/source.svg` командой `npm run app:icons`. Сгенерированные PNG/ICO/ICNS и каталоги `src-tauri/gen/` и `src-tauri/target/` не коммитить.
- Firebase Realtime Database и Anonymous Auth продолжают использовать существующие Firebase compat SDK из Google CDN. CSP в `src-tauri/tauri.conf.json` должен разрешать только необходимые Google Fonts, Firebase SDK, Firebase Realtime Database WebSocket и Firebase Auth endpoints; при изменении Firebase-интеграции синхронизировать CSP.
- Android native-проект создаётся командой `npm run app:android:init`; он намеренно генерируется в CI и локально, а не хранится в репозитории.
- В `package.json` обязателен скрипт `tauri`, вызывающий закреплённый `@tauri-apps/cli`: сгенерированный Android Gradle/Rust-плагин запускает `npm run tauri` и передаёт ему аргументы сборки. Не удалять этот bridge-скрипт; отсутствие приводит к `npm error Missing script: "tauri"` на всех Android ABI.
- Workflow `.github/workflows/build-apps.yml` собирает macOS Apple Silicon, macOS Intel, Windows x64 и Android APK только при ручном запуске из `main`. Обычный push в `main` не запускает нативные сборки: он выполняет frontend-проверки и OTA-публикацию.
- Нативные установщики пока не подписаны сертификатами разработчика: для распространения macOS нужны подпись и notarization, а для Android — release keystore. Подпись OTA-манифеста не заменяет подпись самих установщиков.
- После изменения нативной части проверять desktop и Android сборки ручным запуском workflow; перед распространением отдельно проверить установку, перезапуск OTA и игровой мультиплеер на реальных устройствах.

### Поле редактора испытаний

- Поле редактора должно визуально и по геометрии совпадать с игровым полем партии: использовать общие классы `.board`, `.board__piece`, `.board__cell`, `.board__cell--wall` и `.game__camera`, а не отдельную декоративную сетку.
- Камера редактора должна центрироваться на стартовой карте, сохранять центр при изменении раскладки и масштаба, поддерживать панорамирование и масштабирование.
- Не создавать отдельный DOM-рендер поля или собственный расчёт точек: черновик отображается штатным игровым рендерером и использует те же точки допустимых размещений. Клики редактора по карте и точке не должны запускать игровой ход, менять статистику или завершать партию; состояние игры до открытия редактора восстанавливается при выходе.
- Название, описание и сложность испытания находятся в отдельной постоянно видимой панели непосредственно под заголовком редактора, а не в сворачиваемом блоке боковой панели.
- Публичные испытания доступны всем для чтения; создавать, редактировать и удалять публикации может только владелец по `ownerUid`.
